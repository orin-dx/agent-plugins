For concurrency:

- `rayon`: CPU-bound, independent work—indexing many artifacts, resolving independent impact candidates, parsing/analysis delegated to Monokl.
- `tokio`: async I/O and service concerns—MCP transport, file watching, concurrent requests, daemon lifecycle.
- Never make the domain model depend on Tokio. A normal CLI invocation should work synchronously.
- Don’t run Rayon CPU work directly on Tokio’s async workers; the service boundary should use a blocking pool or delegate it to Monokl.

For storage, I’d start with `rusqlite`, not an async database abstraction. Wisp is local-first and SQLite has a single-writer model anyway. A `wisp-service` process can own the write connection; readers use short transactions or immutable snapshots.

Useful later additions:

- `notify` for daemon-mode invalidation after filesystem changes.
- `zstd` if cached briefing/source snapshots become materially large.
- `petgraph` only if artifact-graph algorithms become more complex than SQL recursive queries and small in-memory traversals.
- `insta` and `proptest` for deterministic output and schema/graph property tests.

Defer:

- `tantivy`: Monokl intentionally avoids a persistent code-search index.
- vector/embedding crates: optional Wisp semantic retrieval feature only.
- `sqlx`: not needed unless Wisp genuinely becomes a networked async service.
- a generic workflow engine: Wisp should provide evidence and state, not become another agent runtime.

The useful heuristic is: **Rayon analyzes, Tokio serves, SQLite relates, Michi renders, Monokl understands code, Wisp decides relevance.**
