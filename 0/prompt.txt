Research results:

[20] assistant: The failure is in the checker design, not necessarily in the diagrams.

`scripts/check-mermaid.sh` runs:

```sh
npx --yes @mermaid-js/mermaid-cli
```

once per Mermaid block. Each invocation resolves the package, starts the CLI, launches Puppeteer/Chromium, renders an SVG, and exits. With diagrams across 13 files, the check times out before reporting a syntax error.

The better approach is to split the responsibilities:

1. Fast required check: validate syntax with Mermaid’s official `mermaid.parse()` API. It does not need Chromium or rendering. Mermaid documents this API specifically for validating diagram definitions: [Mermaid usage](https://mermaid.js.org/config/usage), [Mermaid parse API](https://mermaid.js.org/config/setup/mermaid/interfaces/Mermaid.html).

2. Optional slower check: retain `@mermaid-js/mermaid-cli` for visual/render validation, but run it separately and less frequently. The CLI is Puppeteer-backed, so browser startup is inherently expensive. [Mermaid CLI documentation](https://github.com/mermaid-js/mermaid-cli/blob/master/docs/already-installed-chromium.md).

What I would change:

- Replace the current render-based `check-mermaid.sh` with a single Node process that:
  - extracts all Mermaid fences;
  - calls `mermaid.parse()` for each block;
  - reports the source file, block number, and line number on failure;
  - detects unterminated fences.
- Add a pinned Mermaid dev dependency and lockfile. Do not depend on floating `npx --yes` resolution.
- Rename the check’s success message from “render cleanly” to “parse successfully.”
- Add a separate explicit render command only if visual validation is genuinely needed, such as:
  - `scripts/check-mermaid-syntax.sh` — required, fast, CI-safe;
  - `scripts/render-mermaid.sh` — optional, slower, useful before releases or when diagrams change.
- Do not add a hook. This is exactly the kind of browser-backed check that can make hooks unreliable and frustrating.
- Keep the existing CI Chromium sandbox configuration only for the optional render check.

The small Markdown fence extractor is acceptable. Replacing it with a full Markdown parser would add more dependencies and complexity without solving the main problem. # Shared OK/FAILED summary for scripts/check-*.sh — keeps their output in
# one consistent shape instead of each script reimplementing it.
#
# Usage: report_check <fail_count> <total_count> <ok_suffix> <fail_suffix>
#   report_check "$fail" "$count" \
#     "plugin(s), all versions agree." \
#     "plugin(s) have version drift. Fix and re-run."
# Prints "OK: $count $ok_suffix" and returns 0, or prints
# "FAILED: $fail of $count $fail_suffix" and exits 1.

report_check() {
  local fail="$1" count="$2" ok_suffix="$3" fail_suffix="$4"
  echo ""
  if [[ "$fail" -eq 0 ]]; then
    echo "OK: $count $ok_suffix"
  else
    echo "FAILED: $fail of $count $fail_suffix"
    exit 1
  fi
}
