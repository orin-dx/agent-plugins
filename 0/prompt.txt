## Schema decision: no new schema

`spec@1.acceptance_criteria` is already an array of free-text testable-proposition strings with `is_error_case`/`judgment_call` flags — nothing about that shape is backend-specific. A component criterion ("when `disabled=true`, the button renders `aria-disabled=\"true\"` and does not fire `onClick`") is exactly as expressible as an API criterion. Inventing `component-spec@1` now would force every downstream consumer (Navigator, Smith, Sentinel) to learn a second spec shape for zero expressive gain — pure cost. **Muse produces `spec@1` and `verdict@1`, same as Scribe (canon).** Revisit only if real Lumen usage hits a criterion shape free text genuinely can't express (e.g. a state-transition table) — not before.

## What Muse does NOT do: scan implementation code

Muse's own brief says "specs and audits UI components." Read literally that risks rebuilding Ranger's (proof's) recon→scanner→adversary→exit-gate hazard pipeline a second time for accessibility hazards — a direct capability duplication. That work correctly stays on Ranger (add an a11y hazard taxonomy reference + wire it into Ranger's default scan/adversary routing, per the earlier session's still-valid recommendation). **"Audits" in Muse's scope means audits the *spec*, not the *code*** — same split as Scribe auditing specs vs. Ranger auditing code. This needs to be explicit in Muse's plugin.json description or it'll get misread.

## Agent roster (3 agents — deliberately smaller than canon's 6)

| Agent | Model/Effort | Cognitive mode | Job |
|---|---|---|---|
| `drafter` | sonnet/medium | authorship | Drafts a component spec@1 from a requirement/design intent — props, variants, per-state observable behavior, accessibility criteria as testable propositions |
| `auditor` | sonnet/medium | adversarial review of the artifact, non-binding | Applies Scribe-auditor's generic tests (testable, unambiguous, no padding) *plus* UI-specific completeness checks (missing interactive states, missing ARIA criteria, invalid prop combinations not marked as error cases) |
| `exit-gate` | opus/high | binding terminal judgment | Default-fail gate before the spec proceeds to Navigator; same retry_count/escalate-at-3 pattern as every other exit-gate in the ecosystem |

Canon's other three agents (`verifier`, `architect`, `drift-checker`) are deliberately **not duplicated**:
- `architect` (finding-report@1 → structural spec@1) is domain-agnostic already — a UI architectural finding routes to Scribe's existing architect, not a new one.
- `drift-checker` (spec@1 vs. workspace) is domain-agnostic already — it works on a component spec exactly as written today with zero changes.
- `verifier` (criterion grounded in requirement@1?) is deferred, not rejected — real risk it catches (drafter inventing ungrounded criteria to please a stakeholder) is much lower for a single-user workload building Lumen directly. Add it later if drift/scope-creep is actually observed, not preemptively.
