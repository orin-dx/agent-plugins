## Why this task exists
While adding a TypeScript 7 semantic backend to `oxc-react-codegen`, we researched what an ADR is for and how it changes for agents. Every claim below was checked against a source or a file. Verify against the files yourself before editing, and mark anything you cannot verify.

Research results:
- **Purpose:** an ADR preserves the motivation behind an architectural decision, so nobody blindly accepts or blindly reverses it (Nygard). One decision per record, one or two pages, immutable. A superseded record stays and is marked.
- **Agents change the failure mode, not the goal.** An agent with no memory reads the code and silently reverses the decision. What it needs is the rejected alternative and the reason. Records must reach it before it edits, so route from the instruction file to an ADR index. Instruction files are context, not enforcement, so anything checkable should be a test, lint or hook. Keep the active set small.
- **Boundary:**
  - ADR: architecture, model, direction, decisions, rejected alternatives.
  - `AGENTS.md`: rules for every session (commands, invariants, style, routing).
  - Spec: required behavior.
  - Docs: how it works today.
  - Agent memory: personal preferences and corrections, per repo, not committed.
  - Commit message: why one change was made.
  - Decisions do not belong in memory. It is unshared and goes stale.
- **AGENTS.md in Claude Code:** since v2.1.277 (2026-09-18) Claude reads `AGENTS.md` only when no `CLAUDE.md` exists in the working directory or above. If both exist, it reads `CLAUDE.md` only, unless `CLAUDE.md` imports it with `@AGENTS.md`.

[37] assistant: Yes. My recommendation is to make Orin’s architecture revolve around a verifiable chain:

**Intent → evidence → judgment → authorized execution → independent verification.**

The projects already cover most of that chain. The integration work needs clearer ownership, stronger evidence contracts, and an evaluation path that actually executes the workflows.

This analysis comes from inspecting the repositories’ current source and design documents. I haven’t run cross-project builds or behavioral trials, so implementation presence and runtime correctness remain separate claims.

The responsibilities should look like this:

| Component | Owns | Important boundary |
|---|---|---|
| Wisp Plugins | Workflow, reasoning roles, artifact production, review | Calls deterministic tools; retains judgment where interpretation is necessary |
| Wisp | Artifact validation, relationships, provenance, task-specific context | Does not own parsing or become the workflow orchestrator |
| Monokl | Code analysis, identities, references, dependency queries, analysis caches | Reports scope and uncertainty; does not decide architectural correctness |
| Michi | Response representation and reusable execution primitives | Rendering must preserve meaning; execution policy belongs to callers |
| Lumen | Observations about sessions, operations, cost, and repetition | Observations do not become canonical project knowledge automatically |
| Prism | Controlled experiments and independent outcome verification | Success requires real execution and checked assertions |
| Callisto | Release decisions, authorized effects, recovery, receipts | Release authority stays outside context compilation |
| React docgen / Panda | Specialized domain information and real consumer workloads | Integrate where domain semantics add value |

That division lets the tools cooperate without turning every repository into part of one mandatory runtime.

A useful end-to-end shape is:

```text
Canonical artifacts + repository state
                    │
             Wisp context assembly ← Monokl / domain providers
                    │
             Task-scoped evidence
                    │
         Plugin / harness judgment
                    │
          Authorized implementation
                    │
        Independent executable checks
                    │
          Verified outcome / receipt

Lumen observes the path.
Prism tests whether changes improve its outcomes.
Callisto handles approved release effects.
```

   Similarly, shared `wisp-contracts` types appear in integration documents without an implemented package, and Prism references Wisp decision IDs absent from its current decision log. These should be recorded as proposals or corrected, not treated as established dependencies. [Wisp’s Callisto assumption](/Users/gabe/Projects/wisp/docs/02-architecture-and-contracts.md:363), [Callisto’s actual boundary](/Users/gabe/Projects/callisto/ARCHITECTURE.md:30).

The deeper architecture work is about six decisions.

First, define authority separately from validity. A document can be schema-valid, saved, committed, approved, or superseded; those are different states. Wisp should expose evidence for each rather than reduce them to one “valid” label.

An ADR explains a decision. A spec defines required behavior. A plan proposes execution. A test establishes an observed result within its scope. When they conflict, the system should identify the conflict and invoke the appropriate correction workflow. Silently choosing whichever artifact is newest would conceal the problem.

Second, make context packets evidence-bearing. For every important claim, the consumer should be able to determine:

- Which source and content digest support it.
- Which analyzer and configuration produced it.
- Whether its search scope was complete or partial.
- Whether resolution was resolved, ambiguous, unresolved, or external.
- What was omitted, unavailable, stale, or truncated.

These properties must survive compact rendering. A smaller packet that erases ambiguity is cheaper to read but less trustworthy.

Freshness also needs more than hashes of included files. Suppose a packet answers “these are all implementations of this interface.” Adding a new implementation can invalidate that answer without changing any previously included file. Selection dependencies—directories, configuration, export surfaces, query scope—matter alongside returned-item dependencies.

Third, keep the caches layered. Monokl should own parsing and code-analysis caches. Wisp should own derived artifact relationships and assembled briefings. Michi can transform the resulting representation.

I would not begin with a universal AST cache shared by Monokl and React docgen. Different parser settings and semantic responsibilities make that a substantial compatibility commitment. Exchange stable results first. Share parsing infrastructure only after measurements demonstrate enough duplicated work to justify it.

Monokl’s proposed immutable publication boundary is the right direction: readers see a coherent old revision or a coherent new revision, and a failed update leaves the old one intact. That remains a specified behavior to implement and prove. [Session API](/Users/gabe/Projects/monokl/docs/spec/08-library-session-api.md:145).

Fourth, encode deterministic prerequisites in executable boundaries. Callisto offers a useful pattern: validated intent, explicit observations, constrained transitions, and receipts derived from actual state. Its write permit also makes dry-run violations harder to express accidentally. [Write capability](/Users/gabe/Projects/callisto/ARCHITECTURE.md:12), [Release transition model](/Users/gabe/Projects/callisto/docs/architecture/release.md:39).

For Wisp, equivalent boundaries could require:

- Matching source digests before reusing derived evidence.
- Valid links before accepting an artifact relationship.
- Explicit authorization before a mutation.
- Terminal command results before recording verification success.

An agent still judges whether a specification captures the right requirement. A deterministic check can establish that its links resolve or its referenced bytes match. Both contribute evidence, but they establish different things.

Fifth, keep telemetry observational. Lumen’s integration document correctly recognizes that Wisp events are annotations on a session, not synthetic agent turns. Its proposed event identity and duplicate handling are useful foundations, but the ingestion path is still roadmap work. [Telemetry status and contract](/Users/gabe/Projects/lumen/docs/11-wisp-and-monokl-telemetry.md:3).

Measurements should distinguish observed values from derived estimates and modeled savings. A compact briefing does not, by itself, prove lower session cost. The agent may request the omitted material later or make an expensive mistake.

Sixth, evaluate correctness before optimizing context. I would compare three conditions on the same fixture:

| Condition | Question it answers |
|---|---|
| Direct access to declared artifacts and files | What does straightforward repository access achieve? |
| Wisp artifact-only briefing | Does deterministic artifact assembly help? |
| Wisp briefing with Monokl evidence | Does code-aware selection add measurable value? |

Record completed criteria, regressions, cost per successful task, repeated reads, briefing latency, and cold/warm analysis work. Keep the model, harness, plugin revision, starting workspace, and verification commands controlled.

This also creates a falsifiable architecture recommendation: Wisp earns additional complexity when it improves successful outcomes or reduces their cost without concealing evidence gaps.

I would deliver it in this order:

1. **Reconcile the architecture documents.** Correct maturity claims, contradictory milestones, nonexistent dependency references, and unclear contract ownership.
2. **Establish one real evaluation fixture.** Capture the starting failure, execute the task, independently verify the result, and make missing checks visible.
3. **Deliver artifact-only Wisp context.** Use the existing validation and graph code; add source digests, staleness checks, explicit gaps, and bounded output.
4. **Complete a minimal Monokl integration.** Start with a working interface and independently checked code facts. Add session reuse once its correctness and benefit are demonstrated.
5. **Add rendering and telemetry consumers.** Preserve canonical structured output; prove compact rendering retains the required distinctions.
6. **Optimize from measurements.** Introduce selective invalidation, warm sessions, broader retrieval, and service mode where the evaluated workload supports them.

I would use additional agents for bounded, independent work: one proving a contract, another implementing its consumer, another checking outcomes. They should work from pinned artifacts and report concrete discrepancies. More agents debating the same incomplete evidence would add cost without addressing the central gap.

Michi’s pipeline implementation may help with specific scheduling, cancellation, and retry needs. Its availability should not determine the system’s topology. Transport retries, artifact revision loops, and retries of external mutations need different policies. [Pipeline implementation](/Users/gabe/Projects/michi/crates/michi-pipeline/src/lib.rs:1).

For guardrails, my default would be typed APIs, explicit CLI checks, repository-native tests, and CI. Hooks should remain thin optional adapters; they should not be the sole place a safety rule exists.

The most valuable next step is **one measured, evidence-preserving vertical slice**: a real task, an artifact-backed Wisp briefing, a plugin consuming it, and independent verification. That will tell us which parts of the broader Orin architecture deserve to grow.
